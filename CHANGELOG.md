## [Unreleased]

### Added

- **An offscreen file-to-PCM decoder, so a render job has an audio source that is not `QMediaPlayer`.** `src/recorder/AudioFileDecoder.{hpp,cpp}` walks `avformat_open_input` → `avcodec` → `swresample` → the existing `AudioQueue::pushAll` seam, which is the missing link in every offline-rendering path in this file. It needs no GUI, no audio device and no network, and its header is a PIMPL carrying **no FFmpeg include**, so including it costs nothing and the FFmpeg dependency does not leak upward. Four measured libav facts, each of which cost real time and each of which is a trap for the render worker that comes next. (1) **swr's default mono→stereo rematrix is −3 dB, not unity.** A mono DC of `0.5f` arrives as exactly `0.353553385f`, bit-identical to `0.5f * 0.70710678...` — swr treats the source as a *centre* channel — while `AudioQueue::pushAll` duplicates mono at unity, so the default made every mono source 3 dB quieter through a decoder than through playback. Corrected with `swr_set_matrix(raw, {1.0, 1.0}, 1)`, and it **must** precede `swr_init`: FFmpeg's own header requires the context be "allocated, not yet initialized". (2) `AVCodecContext::frame_size == 0` for `pcm_s16le` is legal and means "codec decides", so every buffer is sized from `swr_get_out_samples()` and the loop is driven by `AVFrame::nb_samples`. (3) A fully drained resample yields **exactly** `av_rescale(inFrames, outRate, inRate)` frames — measured 4000@8k → 48k = 24000 and → 44.1k = 22050, no residual deficit — so the final `swr_convert(..., nullptr, 0)` flush is load-bearing rather than hygiene: without it the total falls short by the filter latency, which is a clipped last syllable and not an error. (4) **A negative result worth keeping: a truncated WAV is indistinguishable from a short one.** `av_read_frame` returns a clean `AVERROR_EOF`, libavformat logs "Packet corrupt" at ERROR only, and it *rewrites* the duration from the bytes it actually read — measured 61125 us for a file whose header declares 0.5 s, i.e. exactly the 489 frames decoded. Same clean EOF for a cut mid-payload, a cut into the header, a `data` size of `0x7FFFFFFF`, and an empty payload. The decoder therefore reports `Complete` and exposes the raw signals rather than inventing a truncation verdict that is not available to it. Two silent-corruption classes are designed out rather than documented. `frame->extended_data` is passed to `swr_convert` and never anything derived from `data[0]`: casting `(const uint8_t*)frame->extended_data` passes the *address of the pointer array*, so swr reads the bytes of a pointer and returns plausible garbage while `got` reports full success (measured `00 08` where the sample was `00 40`), and AAC is planar FLTP so `data[0]` alone silently yields one channel. And a zero-frame audio stream is its own error rather than `EndOfStream`, because a caller checking neither chunk count nor frame count renders a zero-length video and calls it a render.
- **A render job model and a bounded render queue.** `src/recorder/RenderJob.{hpp,cpp}` and `RenderQueue.{hpp,cpp}` are the piece the backlog called the product's missing centre. `RenderQueue` hands a job to an injected `JobRunner` and is then told what happened, so it owns the parts that are genuinely hard to get right — attempt accounting, settle-once transitions, cancel — and knows nothing about what a GL context is, which is what makes it testable with no drawable present. Three decisions, argued rather than defaulted. **`kDefaultMaxConcurrent` is 2, not the `DownloadQueue`'s 3**, because a render job is one GL context plus an 8.3 MB per-frame readback, and the concurrency that is safe for three in-flight HTTP replies is not the concurrency that is safe for three renderers. **`isTerminal` includes `FailedRetryable`**, because `fail()` only settles into it once `kMaxAttempts` is spent: a state that is transient per-transition and terminal per-state is exactly the kind of thing a queue loop gets wrong by re-dispatching an already-dead job. Batch progress is **frame-weighted**, because per-job progress makes a 1-of-4-jobs batch read 25% while 98% of the frames are already on disk. The receipt schema is versioned from the first byte, because the first schema wins forever and a later migration is a support burden nobody can answer for.
- **Burn-in: karaoke rendered into the pixels, as a re-runnable post-pass.** `src/recorder/SubtitleBurnIn.{hpp,cpp}` reads a finished file plus an `.ass` and writes a new one with the text drawn in, re-encoding video with the input's own codec and parameters and **stream-copying the audio** — a three-minute audio re-encode would give away the cheapness that motivates the pass. This is the composability the backlog wanted: change the styling and re-run a short pass instead of re-rendering the video. **The dependency is genuinely optional, which was the hard requirement:** `CHADVIS_FFMPEG_COMPONENTS` `FATAL_ERROR`s on a missing component, so naively adding `avfilter` there would break the build on every FFmpeg-4-era container and stripped distro — *including the Suno client*, which has nothing to do with video. Instead `CHADVIS_POSTPROCESS` (default `ON`) probes `pkg_check_modules(AVFILTER QUIET …)`, `cmake/Sources.cmake` populates the source list only when found, and `TargetSetup.cmake` sets `CHADVIS_HAS_AVFILTER=1` **PUBLIC** so the test binary compiles the same assertions against the same answer. Verified both ways: `SubtitleBurnIn.cpp` is the only file that includes `<libavfilter/*>` and it compiles clean **with and without** the macro, so a build without libavfilter configures, links, launches, and reports itself unsupported at runtime with a reason naming `CHADVIS_POSTPROCESS`. **Two runtime gates checked independently, which is the case worth not missing:** libavfilter built without libass links perfectly and has **neither** the `ass` nor the `subtitles` filter. Both exist here (measured with `avfilter_get_by_name`), and libass turned out to be a dependency *of the filter* — `otool -L` shows `libass.9.dylib` on `libavfilter` and not on `libavcodec` — so there is no separate `find_package` to write. `burnInUnavailableReason()` distinguishes "no library" from "no filter", because the two produce identical symptoms. **Two silent-failure bugs were caught before shipping, and this is the part worth keeping:** the options dictionary was passed in `avfilter_graph_create_filter`'s `opaque` slot instead of `args`, and the `source → render` link was missing entirely. Both compile, link, and fail only at `avfilter_graph_config` with an EPERM that names neither the cause nor the file. Neither would have been found by reading the code, and the same two mistakes are easy to repeat for the remaining filters. **The pixel assertions are measured, not hoped for:** a cued frame differs in 414 luma samples with **all 414 in the bottom eighth and none above** — exactly where the writer's `Alignment: 2` / `MarginV: 10` places them — and a frame with no cue is **bit-identical**. That pair is what separates a real burn-in from a pass that merely copies its input, or one that dirties every pixel with a lossy re-encode. The input is asserted byte-identical afterwards, and the pass **refuses to overwrite an existing output** so a comparison render is not lost. Every entry point returns `Result`, and the post-pass's own writes go through the `classifyWriteResult` discipline from the recorder P0, so a muxer that refuses a packet is an error rather than a truncated file reported as finished. **Not wired yet:** no QML entry point, no bridge method, no config key — and where the `.ass` comes from at burn time (re-reading the sidecar needs no lyrics at all) is a product decision rather than an oversight. Two known edges: the script is authored at 1920×1080 while the encode may be any size, so a 4K burn renders 1080p-authored text at 4K with 4K margins — that belongs in the writer, not the pass; and an unresolvable font would render nothing with a non-obvious diagnosis, since Arial resolves here but a minimal box falls back to fontconfig's default.
- **Recordings can now carry the karaoke track as a real subtitle stream.** `LyricsBridge::assDocument()` already produced a complete `.ass` document; it is now muxed into the encoded file, so a player shows selectable, per-word karaoke without the user handling a sidecar. **Container constraint, measured rather than assumed:** `avformat_query_codec` returns `1` for Matroska and `0` for MP4, MOV, WebM and AVI on this FFmpeg, so **only MKV can carry ASS**. The gate is therefore load-bearing rather than defensive: without it, MP4 — the default output — would gain a subtitle stream that `avformat_write_header` rejects, failing *every* MP4 recording. That was verified with standalone probes rather than from the `ffmpeg` CLI, because the CLI fails in `init_muxer`'s tag lookup at write time, a different code path from the query. **There is deliberately no `mov_text` fallback**: MP4 answers `mov_text=1, ass=0`, so its only text codec is 3GPP timed text with no override-tag syntax — a `\kf` cue would be flattened to plain text, i.e. the feature appearing to work while being precisely what it must not be. `initSubtitleStream` returns `void` by design, so no subtitle outcome can ever fail a recording: no lyrics, an unusable container, or a malformed document all yield a normal playable file with a `LOG_INFO` saying why the track was dropped. Cues are emitted on the **video clock** rather than up front, because writing a three-minute lyric sheet in one go would exceed `av_interleaved_write_frame`'s 10000-packet interleave default and return `EAGAIN`, silently dropping cues. `AV_DISPOSITION_DEFAULT` is set because Matroska's `mkv_default_mode` marks a subtitle *not* default, so without it the track ships switched off and nobody sees it.

### Fixed

- **`--headless --record` is now refused at startup instead of silently never recording.** Recording is wired to the visualizer window's GL context at init time — `frameCaptured` → `VideoRecorder`, `RecordingBridge::setVisualizer`, all inside `if (!opts.headless)` — so headless recording cannot produce a file: no window, no frames. The launcher accepted the combination and ran a batch session that never recorded anything. The combination is now rejected after argument parsing, order-independent, with the same error convention as every other parse failure (exit 1, "Try --help"). The argv parser moved verbatim into a pure static seam — `Application::parseArgsFrom(argc, argv)` — so tests can drive real argv without constructing an `Application` (whose destructor tears down the global logger mid-test-binary); `parseArgs()` is now a one-line delegate. `tests/unit/core/test_CliArgs.cpp` is the CLI parser's **first coverage ever** (T0100 listed it as untested): each flag parses alone, and the combination is refused in both orders and through the `-r` short form. One honest finding recorded for the board rather than silently expanded into this fix: `--record` *without* `--headless` is also a no-op today — `opts.startRecording` has no reader in any mode; wiring a GUI auto-record is un-prescribed feature work.
- **A short download can no longer be renamed into place and reported `Completed`.** `DownloadQueue` never compared the bytes it received against the bytes the transfer promised: a 2xx whose connection closed at 90 % arrived with `NoError`, so the plausible-looking prefix was promoted from `.part`, tagged, sidecarred and announced `Completed` — a file that plays to the break and that no downstream consumer can tell apart from a real download. Each item now records the promised total (the `downloadProgress` total, with a Content-Length fallback at finalize time), and `finalizeSuccess` compares before any byte is promoted: a truncated transfer fails with a new `ShortDownload` cause — distinct from `ShortWrite`, the disk-full write-side cause — named by exported, test-asserted wording ("downloaded N of the M bytes the server promised"), and retried like any other transient transport failure, bounded by `kMaxAttempts`. A transfer that reported no total at all is deliberately not failed: there is nothing to compare against, and failing it would break every legitimate unknown-length transfer. **The retry path also stopped leaking the `QNetworkReply`:** the retry branch returned without `deleteLater()` or clearing `item.reply`, so the next attempt's assignment orphaned up to `kMaxAttempts-1` replies per item, each still holding its connection and buffers. A `QPointer`-based regression test proves the failed reply is destroyed the moment the retry is scheduled. And the board's third item in this cluster — the `cancel()` use-after-free — turned out to be **already defused** by the earlier `shared_ptr`/`weak_ptr` containment rework: the re-entrant `abort()` → `finished()` → `retire()` chain keeps the item alive through the whole call, and `cancel()` dereferences nothing after `abort()`. Closed with instrumented evidence instead of a re-fix: the whole `DownloadQueue` suite — cancel-in-flight included — passes under a fresh ASan build, whose run then went on to abort on a *pre-existing, unrelated* container-overflow in the lyrics plausibility checker, filed as new board item T0178 — the first catch of exactly the ASan lane T0043 said this tree was missing.
- **The `/oc` comment agent no longer runs for any GitHub account that types the command.** The `opencode` workflow — a job holding `id-token: write` plus the `OPENCODE_API_KEY` secret — triggered on a comment body containing `/oc` or `/opencode` with no check on who commented, so any account on GitHub could start a secret-bearing agent job with one comment. The gate is deny-by-default: the job's `if:` now requires the command match **and** an `author_association` of `OWNER`, `MEMBER` or `COLLABORATOR`. The parentheses are load-bearing — GitHub's expression grammar binds `&&` tighter than `||`, so an ungrouped form would have attached the association check to only the last of the four body conditions and left the other three paths ungated. The third-party action is also pinned from the mutable `@latest` tag to the immutable commit SHA `2c14fc5586fe0b88e5c04732d2e846769cc35671` (resolved from the tag, provenance inline), closing the supply-chain half that `.github/dependabot.yml` was written to track; `actions/checkout@v7` stays on its major tag deliberately, being first-party and the exact ref dependabot manages. Static-audited against the agentic-CI rubric: no `run:` steps exist, no `${{ github.event.* }}` interpolation outside the guard, no `pull_request_target`, no `ref:` checkout, and `persist-credentials: false` was already set. Runtime confirmation is post-merge: a non-member typing `/oc` must produce no job run.
- **A live session can no longer be signed out by the number "401" appearing in any text.** `isAuthFailure` — the single gate between an HTTP reply and a full session teardown (bearer dropped, pending auth work flushed, `NeedsReauth`, `needsReauth()` emitted) — substring-matched `"Unauthorized"` and `"401"` in the error message. It was called with the raw server text on the lyrics path and with Qt's `errorString()` — which embeds the full URL on transfer errors — on the client path, so a byte count (`4012 bytes`), a clip id, or a path segment containing those digits flipped a healthy client to `NeedsReauth` and dropped the bearer: a self-inflicted sign-out with no server involvement. The classifier now takes the HTTP status and nothing else — `401` or `403` — and the string parameter is deleted outright, so the old failure shape cannot be written again; a caller with no status (transport errors read as `0`, the old lyrics call site passed `-1`) is by construction not an auth failure. The lyrics manager's queue-clear on session death moved to the real channel it should always have used — `SunoClient::needsReauth`, documented "touch/retry chain exhausted; user must supply fresh credentials" and emitted at exactly two teardown points — making it the sixth consumer of that signal instead of the lone text-matcher of the global error broadcast. First coverage the classifier has ever had pins the status axis, `402`/`404`/`429` included: a rate limit must never sign anyone out.
- **The preset panel's buttons and the overlay delete are pressable again.** In both `PresetDelegate` (`PresetsPanel.qml`) and `OverlayDelegate` (`OverlayPanel.qml`), the whole-row `MouseArea { anchors.fill: parent }` was declared **last** — and QML stacks later-declared siblings on top for input delivery, so the full-bleed area sat above the favourite and blacklist `AppButton`s, every star-rating `MouseArea`, and the overlay delete button, and ate all of their clicks: favouriting, blacklisting, rating and overlay deletion were impossible in the shipped UI. The row `MouseArea` is now declared **before** the controls in both delegates — the exact arrangement `ClipCard.qml` documents as the correct pattern ("declared after the card-wide MouseArea, so it takes the click rather than needing a hit-test rectangle"). Hover styling (`containsMouse`) and the row-level gestures (double-click select, single-click select) are unchanged; only the stacking order moved. This also retires the board's T0073, which cited the very same trailing `OverlayPanel` MouseArea while claiming to be "a different panel" than T0004.
- **Star ratings write onto the rated row, not preset #0.** Inside the star `Repeater { model: 5 }` of `PresetsPanel.qml`, `modelData` is the **star number 0–4**, so the click handler's `modelData.index` was always `undefined` — coerced through the `int` parameter to `0` — and every star click rated preset #0 while the clicked row never changed. The row's identity now travels on a real delegate property, `PresetDelegate.presetIndex`, which the Repeater's shadowing cannot hide, and the click passes it to `setRating`, which writes the preset the full-list index actually addresses. The board's original suggestion ("pass the outer preset's name") predates the index key: `setRating` is index-addressed, no name-keyed overload exists, and inventing one would fork the identity model the panel just converged on. `TestPresetBridge` gained the rating case — a filtered row's index must rate that row by name in `RatingManager` and leave slot 0 untouched.
- **Preset rows act on themselves again — every click in the panel hit preset #0.** `PresetBridge::presetToVariant` handed QML `name, path, author, category, favorite, blacklisted, playCount, rating` — no `index` — while `PresetsPanel.qml` passes `modelData.index` into every index-based slot (`selectByIndex`, `toggleFavorite`, `toggleBlacklisted`, `setRating`). An undefined value coerced through an `int` parameter is `0`, so a click on any visible row selected, favourited or rated preset #0 regardless of the row. The misdirected favourite/blacklist write is the poisoning kind: `setFavorite`/`setBlacklisted` insert the *wrong* name into the persisted name sets, which the next rescan re-applies by name, so the wrong-row write survives rescans while the clicked row never gains its star. The emitted `index` is deliberately the position in the **full manager generation**, not the row's visible position — the panel renders `filteredPresets()`, so under any search or category filter the two diverge, and every QML-facing index slot addresses the full list (`setRating` literally pins `allPresets()` and indexes `(*presets)[index]`). `toVariantList()` derives it by pointer arithmetic against the pinned generation's storage, the documented `PresetView` contract and the same idiom `selectRandom()` already uses, so no O(n·m) lookup was added. The QML needed zero changes: the panel's callsites were correct as written and read a key that finally exists. `tests/unit/visualizer/test_PresetBridge.cpp` is the first coverage `PresetBridge` has ever had and pins the contract bridge-side — a filtered row must select and favourite *itself*, never slot 0. The star-rating call inside `Repeater { model: 5 }` is a different defect (`modelData` there is the integer 0–4, T0003) and is untouched.
- **The Settings window can open again, so sign-in is reachable at all.** `navigate("settings")` called `settingsWindowApi["open"]()` — and `QQuickWindow` exposes `show()`, `raise()`, `requestActivate()`; there is no `open()`. Every path into Settings (the nav rail, the account chip) threw `TypeError: settingsWindowApi.open is not a function` after assigning `activeView = "settings"`, which blanked the content area too — and since the one window holding both Google sign-in and the manual cookie paste is the Settings window's Account page, the app had no reachable sign-in path at all. The `var`-typed alias is why the typo could ship: it erases the very type a QML compiler pass would check. It is deleted, the window is addressed by its typed id, and it gains `objectName: "settingsWindow"` so C++ tests find it by identity instead of position — VideoView's native container is also a `QQuickWindow`, so "the second window in the tree" is not a fact that survives an edit. The call now branches on visibility: `show()` for a closed window, `raise()` + `requestActivate()` for one already up, because an `ApplicationModal` `show()` may run a nested event loop that only returns when the window closes, making activation calls placed after it no-ops. Guarded by the tree's first behavioural test of this surface — `integration_tests::settingsWindowOpensOnNavigate` drives the real `navigate("settings")` offscreen, asserts the window comes up and that QML reports no error, and arms a watchdog so a modal `show()` can never hang the suite. Proven red first (restoring the broken call fails the test, naming the symptom), then green, plus a real cocoa launch: the app's own log shows `visible=true`, `size=900x680`, `title="ChadVis Settings"`, `page=0` (Account), no TypeError, clean shutdown.
- **The muxer takes ownership of the packet and blanks it, and four call sites were reading it afterwards.** This is the one defect that made `RecordingStats.bytesWritten` permanently `0` — video, audio and subtitle alike — for the entire life of the recorder, so `RecordingBridge::fileSize()` has displayed **"0 B"** to the user for every recording ever made. `av_interleaved_write_frame()` consumes the packet on success: measured, `size` is 73 before the call and **0 after**, with `pts` reset to `AV_NOPTS_VALUE`. So `bytesWritten += packet->size` added nothing for every successful write. It is the most plausible-looking instrumentation bug there is: it is wrong only in the direction of *under*-reporting, and under-reporting a byte count is not a shape any existing assertion was looking for. **This is not a regression from `1e3c0fa`, and that distinction is the useful part:** `git log -L` shows the line was written that way when the file was created, and the four tests that caught it are **new** in that commit — so this is a decade-old latent bug caught by new tests, which is the system working exactly as intended. The fix is to capture the length **before** the muxer runs. It had **four** instances, not one: the video, audio and flush write paths in `VideoRecorderFFmpeg.cpp`, plus one that belonged to nobody at the time — `SubtitleBurnIn.cpp` read `out->size` after the same call and consequently logged `Burn-in wrote <file> (0 bytes)` **on every single successful burn-in**, which is precisely the class of message a reader learns to ignore.
- **A frame the encoder was still holding counted as written.** `encodeVideoFrame` and `encodeAudioFrame` returned "written" when `avcodec_receive_packet` returned `AVERROR(EAGAIN)` and produced **zero packets**, so `audioFramesEncoded_` incremented for a frame that reached no file, `anyFrameWritten` reported true on an otherwise empty audio track, and the user-facing stop reason composed from it was wrong. This is not an edge case: **measured against this box's FFmpeg, native `aac` declares `AV_CODEC_CAP_DELAY` with `initial_padding = 1024` and emits `0,1,1,1,1` packets over its first five sends**, so it fires on the **first audio frame of every recording**. The two identical bodies collapse into one private `encodeOneFrame` returning `FrameEncodeOutcome{Deferred, Written, Lost}`, which makes the distinction a type instead of a comment: on audio only `Written` counts and `Deferred` is neither progress nor fault, on video anything but `Lost` counts. **A prediction in the original brief was wrong and the measurement corrected it:** FFV1 and libx264 both declare `AV_CODEC_CAP_DELAY` yet both emit **1 packet on send #0** (`has_b_frames = 0`, `initial_padding = 0`; measured ffv1/mkv payload 87 bytes, libx264/mp4 payload 1353). Video's lenient mapping therefore has **no reachable `Deferred`** with this project's codecs and was **deliberately left alone**: tightening it would change a contract nothing can observe, while loosening it would break the audio side where it is load-bearing. The assumption is now pinned by a test rather than by a comment, because an unpinned assumption about a codec is a comment.
- **`[recording.video]` and `[recording.audio]` were never written at all, so no encoder setting has ever survived a save.** `ConfigParsers::serialize` built both sub-tables in locals named `videoOut` / `audioOut` — but `VC_SER_FIELD` expands to `out.insert(...)`, a name the macro never sees. Both sub-tables were therefore emitted **empty**, every encoder key landed **flat** in `[recording]`, and `video.codec` and `audio.codec` collided on one key, where toml++ keeps the first and the **audio codec was silently lost**. Coming back in, the parser read an empty `[recording.video]` and reset codec, crf, preset, pixel_format, width, height, fps and bitrate to defaults: a user could set CRF 18, watch it persist, and get the default back on every launch. Fixed by shadowing `out` per group inside a `recordingOut` section table, and guarded by a `roundTripPreservesEveryField` test. **This is the most consequential correction of the session, because `TODO.md` carried a verified-looking `[x]` — "Recording video/audio settings persist … No bug" — that was never verified.** The bug is present at `HEAD` and predates this work entirely. A `[x]` nobody re-derived is exactly the `AGENTS.md` §3 failure, and it survived precisely because it read as settled.
- **`AudioQueue::pushInternal` under-counted drops by up to 64x.** It stopped at the first refused 8-frame chunk, counted those 8, and returned **without accounting for the remainder** — so 512 frames pushed into a capacity-1 queue reported **8 dropped / 504 accepted** while `totalPushed_` counted all 512. The number that feeds any lossless-render assertion was wrong by exactly the factor that would let such an assertion pass.
- **A secret can no longer reach `config.toml`, because the serializer physically cannot emit it.** `token` and `cookie` sat in the **shared** `CHADVIS_SUNO_FIELDS` table, which `serialize` expands, so the only thing standing between a one-year Clerk refresh credential and a mode-`0644` file on Arch and Windows was a **code comment**. They now live in a parse-only `CHADVIS_SUNO_LEGACY_SECRET_FIELDS`, which `parseSuno` expands and `serialize` does not — converting the comment into a compile-time guarantee, which is what `AGENTS.md` §2 actually demands when it asks for evidence. Alongside it: `ConfigLoader::load` gained a `catch (const std::exception&)` backstop, `[overlay] enabled` is a real round-tripping field rather than a hardcoded `true`, and `ConfigLoader::save` is now atomic **and portable** — `MoveFileExW(MOVEFILE_REPLACE_EXISTING | MOVEFILE_WRITE_THROUGH)` on Windows, `fsync` + `rename` elsewhere — where the rename-over-existing case is the one that fails on the major userbase. A live null-deref went with them: `toml::table_view::get()` returns a **raw `const node*` that is `nullptr` for a missing key**, so any config with a `[general]` table and no `debug` key dereferenced null. **`aspect_correction` and about a dozen other keys the serializer emits were absent from `config/default.toml`**, so a first run wrote a file the shipped default did not describe — and `aspect_correction` is the one that silently decides whether a vertical render is letterboxed or squashed.
- **A JWT with no `exp` was accepted as valid forever, at four call sites.** `expiryEpochSecs` returned `0` when `exp` was absent, and `isExpired` then did `if (exp <= 0) { return false; }`, i.e. never expired. A new `JwtUtils::hasUsableLifetime` requires `exp` present, integral and in the future, with `expiryDefect` returning one of four named reasons so a rejected paste can say which — mirroring the existing `noClerkCookieReason` pattern rather than inventing one. **The backlog named three call sites; there are four, and the fourth is the one users actually hit.** `SunoClient`'s `StoredCredentialShape::BearerToken` arm took a pasted JWT straight to `applyBearer` with **no expiry check at all**, installed it as `ActiveValid`, persisted it to `suno/bearer`, and armed no refresh timer — so a pasted token with no `exp` stayed live until the server 401'd it. **No signature verification was added, deliberately:** a native client cannot verify RS256 against Clerk's JWKS without shipping a key-distribution dependency, and TLS plus the captured-host boundary is the correct substitute. The defect was the fail-open on a *missing* claim, and that is what closed.
- **`loadM3U` no longer turns any line starting with `http` into an unauthenticated fetch.** The remote branch is **gone**, not gated, and no replacement classifier was added — because every legitimate remote track already arrives through `DownloadQueue`, which validates the host, while an `.m3u` from any download, shared drive or forum post could otherwise make the client issue a request to an arbitrary host, with `http://169.254.169.254/latest/meta-data/` becoming a track and probing the LAN. The same URL-shaped predicate still exists, but it now touches **only the log message**: it decides how to describe a skipped line, not what to do with one. That is the shape worth preserving, because a URL-shaped predicate that can only reach a log line cannot be an SSRF primitive.
- **`sanitizeFilename` normalises, budgets and reserves; two `SunoDownloader` defects went with it, and the serious one was not in the helper.** NFC normalisation through Qt's own tables, because APFS stores NFD and so a composed title round-trips to different bytes while two visually identical titles collide; a byte budget that never splits a UTF-8 sequence, so a 300-byte title no longer yields an `ENAMETOOLONG` on ext4/APFS; Win32 reserved device names checked **last** and *after* trailing-space-and-dot removal, because Win32 strips those from every path component before it reads the name — which is the entire reason `CON .mp3` used to survive a check `CON` did not, and why truncating `COM11` to three characters can *create* a reserved name; and NUL mapped rather than truncating. Seventeen exact-value tests in a new `tests/unit/util/test_PathSafety.cpp` prove it single-component and traversal-proof. **The important half was elsewhere:** `clip.id` was interpolated into a filesystem path **unsanitized** while `ClipParser::parseClip` validates only non-empty, so an id containing `../` wrote outside the download directory and needed nothing more than two clips sharing a title, which is the normal case for generated music. `destOwner_` is also keyed case-insensitively now, because `Song.mp3` and `song.mp3` are different map keys and the same file on APFS and NTFS, so the first was silently clobbered.
- **`Color` moved to `src/util/Color.{hpp,cpp}` with a non-throwing parse and four distinct verdicts.** `parseHexColor` returns a `std::expected<Color, ColorParseFailure>` instead of a silent fallback. **The backlog's description of the old behaviour was wrong twice:** `accent_color = "blue"` does **not** throw and does not return black — a 4-character word falls through to the default-constructed `Color`, which is **opaque white**. It throws only on 6 or 8 characters of non-hex (`'zzzzzz'`, `'#gggggg'`). The `std::stoi` throw is still reachable, which is why the `ConfigLoader` backstop above matters.
- **Audio device settings are real, and one of them is a lie Qt will not let us fix.** A new `src/audio/PcmFormat.{hpp,cpp}` (`vc::pcm`) centralises sample-format handling, `AudioEngine::init` takes an optional `AudioConfig`, and device enumeration plus status reach `SettingsBridge` and `AudioSettings.qml`. `Int32` is now handled, where it previously fell through and pushed the **previous** buffer's samples into both the visualizer and the recorder with no diagnostic. **A premise in the original brief was false and the installed header settles it:** `QAudioOutput::errorChanged` **does not exist in Qt 6.11** — `error()`, `state()`, `setBufferSize()`, `setSampleRate()` and `start()`/`stop()` were all removed with the Qt 5 redesign, leaving only `device`/`volume`/`muted` and three `…Changed` signals. `deviceChanged` and `QMediaDevices::audioOutputsChanged` are connected instead, which covers a device being unplugged but not a device *erroring*. The consequence is structural rather than cosmetic: **`audio.bufferSize` has no device-level home in Qt 6 at all**, so it now sizes the engine's conversion window and the actually-delivered sink rate is observed and shown rather than requested.
- **The download path is bounded, and one of its bugs was a use-after-free found under ASan.** `DownloadQueue` now checks `write()`'s return, so an ENOSPC mid-download can no longer rename a truncated `.part` into place and report `Completed` for a file that will not play. It opens the scratch file `WriteOnly|NewOnly` — **`NewOnly` *is* the cross-platform `O_EXCL`/`CREATE_NEW`, so no raw `::open` is needed**; measured here, `NewOnly` fails on an existing file and on a symlink, where `WriteOnly|Truncate` succeeds and **clobbers the symlink target**, which is a real primitive rather than a theoretical one. Each item is capped at 256 MiB, checked **before** the write with strict `>` so exactly-at-the-limit succeeds, and every scratch unlink is gated on an `ownsPart` flag set only by a successful exclusive open, because a path another writer holds a lock on is not yours to delete. **Two corrections to the original brief, both measured:** `TransferTimeoutAttribute` **does not exist** in Qt 6.11 — the API is `setTransferTimeout(int)`, **Qt 6.7+**, and `cmake/Dependencies.cmake` pins no minimum — and its documented semantics are "abort if *no data is exchanged*", making it an **idle/stall deadline, not a total-transfer deadline**, which is the only reason it is safe for media at all. Unset means zero means no timer, so the tree genuinely had none. The use-after-free is worth recording as a shape: the old `[this, &item]` connection pattern left a **guaranteed** window, because tearing an attempt down from inside `readyRead` runs abort → finished → terminal state → the reply's next `downloadProgress` after the item is freed. Containers now hold `shared_ptr` and connections capture `weak_ptr`, so an expired pointer is the honest answer instead of freed memory.
- **The recorder reported a successful start it never had, and "completed" files it failed to write.** Two independent lies in the one component whose entire job is producing a correct file. `VideoRecorderThread::start()` returned `void` and swallowed an `ffmpeg_.init()` failure, so `VideoRecorderCore` set `state_ = Recording` and returned `ok()` regardless — an unwritable output directory, a missing codec, or a bad container/codec pairing produced a UI showing an **active recording** with a running timer, no file, and no error. It now returns `Result<void>`, and only enters `Recording` on genuine success, setting a **reachable, recoverable `Error`** state and zeroing the counters *before* announcing the transition (the bridge snapshots the stats at exactly that moment). A state nobody could recover from would have been a worse bug than the one being fixed, so `start` and `stop` both accept `Error` and perform normal transitions. Separately, `writePacket`'s return was discarded by both callers while `framesWritten` incremented regardless, so **disk-full at 90% produced a truncated MP4 that opens and plays to the break point and was reported `Completed`** — worse than a failed recording, because it is a plausible-looking one. The muxer return is now classified `Written` / `Backpressure` / `Failed`; `Failed` sets a sticky flag, the loop stops producing and reports once, and `stop()` names the likely cause. **The judgement call: `EAGAIN` is backpressure, not failure.** Folding it into failure would mark a merely-slow recording as broken — the same class of lie in the opposite direction — so a backpressured packet is not counted (it genuinely is not in the file) but is not treated as damage, and it logs once rather than once per frame. Also fixed: both `av_frame_get_buffer` returns, both `swr_*` returns (discarded while `swrCtx_.get()` was dereferenced by the very next call), and `av_write_trailer` — without which an MP4 has no `moov` atom and a file that will not open. **A latent null-deref surfaced en route:** after a failed init the destructor's `stop()` reached `av_interleaved_write_frame` on a context with either no `pb` at all or no header written, so the `headerWritten_` gate now covers the flush and trailer paths too. Four of the five production fixes are guarded by reasoning about what cannot fire rather than by a test, because there is no portable way to induce OOM or a null resampler in-process; the two behavioural tests are real, and both fail on the old code.
- **Every karaoke cue would have been written 100x too small.** The centisecond→millisecond conversion was `cs / 10`, where `kMillisecondsPerCentisecond = 10` names a **multiplication**. So a two-second cue was written as 20 ms, and a three-minute song's entire lyric sheet would have collapsed into its first 1.8 seconds, stacked on itself. Two sites divided — the cue's own `pts`/`duration` and the video-clock interleave gate — so they **agreed with each other and disagreed with reality**, which is why nothing upstream could see it, and `timingsMs[0].first == 0` passed by coincidence because `0/10 == 0*10`. The conversion is now a single named `toMilliseconds()` used by all three call sites. **Only an exact-value assertion could have caught this class**: "the duration is non-zero" or "roughly 2 s" would have passed on every version of the bug. Caught before it could ship.
- **A broken test reader was masking that bug, by cancelling it out.** The recorder suite's `readEncodedStreams` had two defects that composed: a missing `continue` let audio and video streams fall through into the subtitle block, so *every* file appeared to have a subtitle track, and a forward-only `av_read_frame` cursor was drained once per stream, giving the first stream the whole file and leaving the real subtitle stream empty. Six tests failed; the reader, not the muxer, caused all of them. Worth recording as a general trap: **a broken reader cannot distinguish "the muxer wrote nothing" from "the reader read nothing"** — and here the reader's own unit error happened to cancel the writer's 100x error, so the test compared two wrong numbers and saw something plausible. The MP4 failure's own assertion text said "the muxer declared an ASS stream in an MP4", which was the wrong conclusion entirely; the absence assertions now report the actual stream table on failure so the reader-vs-muxer question answers itself in one look.
- **The ASS assembler moved out of the QML bridge.** `src/recorder/` must not reach up into `src/qml_bridge/`, so `toAssDocument` now lives in `src/lyrics/LyricsData.{hpp,cpp}` under the existing `LyricsExport` namespace and both the bridge and the recorder call it — still exactly one assembler. `VideoRecorderFFmpeg.hpp` names no lyrics type and takes the document as opaque bytes. Production wiring runs `RecordingBridge → VideoRecorderCore → VideoRecorderThread → init(settings, assSubtitle)` with every hop defaulted to `{}` so all pre-existing call sites are untouched, and the bytes are copied into the encoder before the `JThread` is created so no borrowed `string_view` can cross the thread boundary.
- **An opt-in ThreadSanitizer lane, so two shipped sanitizer claims become reproducible.** The changelog asserted "AudioAnalyzer concurrency tests pass under ThreadSanitizer" and the backlog credited the PFFFT fix with "normal and ThreadSanitizer tests" — but there was no `-fsanitize` anywhere in `CMakeLists.txt`, `cmake/`, `tests/` or `scripts/`, and all 29 `sanitize` matches in the tree were `sanitizeFilename`. Both claims described an ad-hoc build that was never captured, which is not a verification a future session can check. `CHADVIS_SANITIZER` is now a cache option in `cmake/Compiler.cmake`, paired with `cmake/tsan.supp` and a `TSAN_OPTIONS` block on the ctest entries. Built and run: **320/320 targets, zero errors, the lane executes, and every test passes under it.** Three design points were load-bearing and all were measured rather than assumed. It is a **cache option, not a target**, because `unit_tests` links `libproject_lib.a` holding all app code — a `unit_tests_tsan` target would link uninstrumented objects, report nothing and exit 0, which is a false-negative generator worse than having no lane at all. Darwin defaults to `abort_on_error=1`, so a ctest entry without `TSAN_OPTIONS=abort_on_error=0` dies with SIGABRT on the *first* finding; `halt_on_error=0` does **not** suppress it. And `CMAKE_OSX_SYSROOT` is actively unsafe here: adding the SDK the compiler already reports for itself drops `/usr/local/include` from `/usr/bin/c++`'s search list, stripping the project's only route to fmt, spdlog, toml++, glm and taglib.
### Fixed

- **A test that blocked a worker thread could turn any failed assertion into an unrecoverable 300-second hang.** `concurrentRestoresCoalesceInsteadOfDoubleReading` blocks the credential backend in `releaseBackend.acquire()` and released it only after several `QVERIFY`s. If one of those failed, `QVERIFY` early-returned, the release never happened, the worker thread stayed blocked forever, and `~CredentialStoreWorker`'s `quit()` + `wait()` hung — the `quit` cannot take effect because the event loop is blocked *inside* the lambda. The real one-line assertion message was buried under a QTest timeout and SIGABRT. **This is build-independent:** any test that holds a worker thread in a blocking wait must arm its release before the first assertion that could fail, because `QVERIFY` is not cleanup and a joining destructor converts a missing release into a hang rather than a failure. Fixed with a scope-guard that releases on every exit path. The sanitizer lane also runs ~5–20x slower, so wait budgets now scale from a `CHADVIS_SANITIZER_BUILD` definition instead of being hard-coded, keeping the normal build's fast timeouts.
- **Suno credential restore has a dedicated readiness worker.** Reading the keychain used to race startup: a surface that asked early got an answer that was really a guess, and the guess was indistinguishable from "no credentials". Restore reads now coalesce on a worker that never drops a caller — a second or third requester attaches to the read already in flight rather than queueing a second one and receiving a different answer — and the Library and Explore surfaces wait for **definitive** readiness instead of proceeding on "not yet". The distinction matters because a keychain round trip is slow enough to lose a race and fast enough to look like a hit: without the gate, a cold start presented an empty library that then filled in underneath the user, with no error and no signal that anything had happened.
- **API master: `POST /v1/client/verify` is resolved to POST, and its purpose is now known.** The route was carried as an unresolved method/contract conflict with a companion Appendix A row; five direct observations in the 2026-08-25 capture settle both halves. It is **POST**, with a form body of `captcha_token` + `captcha_widget_type=invisible` + `captcha_action=heartbeat`, and a **204 No Content** response. It is a captcha-gated Clerk session heartbeat, corroborated three independent ways: the form field is literally `captcha_action=heartbeat`, the Clerk instance reports `captcha_heartbeat: true`, and the calls sit 1–8 minutes apart with no other traffic on the instance to explain them. The useful part of the resolution is negative and now **proven** rather than merely prudent — a 204 with no body cannot return a bearer, so this route definitively cannot be used for token refresh, which is what the "leave the Clerk `tokens` route unwired" conclusion rested on. The route stays `not-in-code` until something needs it. `/v1/verify` is a **different, still-unobserved** route and is kept separate in four places so a future reader does not merge the two on the shared prefix.
- **API master: two captcha systems that were previously conflated are now distinguished.** The Clerk auth captcha is **Cloudflare Turnstile** — `captcha_provider: "turnstile"`, `captcha_heartbeat: true`, `captcha_widget_type: "smart"`, plus a managed and an invisible sitekey — and the tokens on the wire carry Turnstile's `1.<payload>.<hash>` shape, which rules hCaptcha out for that route. The suno.com web sign-in UI captcha is **hCaptcha**, recorded from the sanitized recon's `api.hcaptcha.com/getcaptcha/…` on the session-recovery pages. The generation captcha is also Turnstile rather than hCaptcha: `TURNSTILE_GENERATION_CAPTCHA_VERSION = 2` with `FORCE_ENABLE_CAPTCHA = false`, and the hCaptcha constant in the client bundle is marked legacy. One rule is now recorded in the master, and it is the part most likely to be re-learned the hard way: **naming a captcha provider adds no captcha host to any allowlist.** An earlier pass at this same work closed by asserting that the generation provider was "still unstated"; that assertion was wrong and is corrected here rather than left to be found again.
- **API master: six OAuth providers are enabled server-side, not just Google.** `GET /v1/environment` reports `identification_strategies` covering Google, **Facebook, Apple, Discord and Microsoft**, an Apple-token strategy and phone number, with `password: "on"` and `preferred_sign_in_strategy: "otp"`. Recorded strictly as an instance-configuration fact — **not** an endorsement, and **not** evidence that any additional provider works through a native loopback callback, which is a separate capture question and the one that actually gates shipping. Apple Sign In is worth recording on macOS specifically because `AuthenticationServices` can produce the `oauth_token_apple` credential natively and would remove a browser round trip; that is a design decision *enabled* by evidence rather than evidence of a design, so it stays in the backlog and not in the master.
- **API master's document map named neither of the two sections it had grown.** A reader could follow the section pointer to the OAuth analysis document, come away understanding the cookie flow, and never learn that the credential *shapes* were documented at all — §3.3 and §3.4 were reachable from inside the document but advertised by none of the entry points. Both the master's document map and `docs/suno_api/README.md` now name them, because the "one fact, one owning document" rule only works if the map is the index and the index is current. Worth recording how it was caught, since both detectors were wrong in **opposite** directions: a first link-checker reported the new anchors broken, and a second reported the long-standing `#appendix-a--explicit-conflict-register` anchor broken. The first collapsed whitespace where the slugger keeps one hyphen per space; the second assumed em-dash stripping left a single hyphen. It runs against a real window, context and projectM, and proves the destination projectM actually draws into, that a bound FBO is ignored, that the capture is non-empty and correctly oriented, that a differing record resolution is scaled, that the live native window captures pixels through its own render timer and buffer swap, and that a 45-frame H.264 encode decodes back to a lit picture. First, **switching `CMAKE_BUILD_TYPE` in place invalidates every object**, turning a one-file edit into a full recompile, so each profile has its own tree: `build/` (Release), `build-fast/`, `build-debug/`, `build-tsan/`, `build-asan/`, `build-ubsan/`. ### Fixed

- **Preset scanning walked the entire preset library on the GUI thread at startup.** `PresetManager` gained `scanAsync` / `rescanAsync` / `setPublishContext` over **shared generations**: every scan builds a fresh vector and *swaps it in*, so a published generation is never cleared, resized or refilled in place, and a `const PresetInfo*` taken before a rescan stays valid instead of dangling into recycled storage. The worker is a `vc::JThread` parked on a condition variable — the `VideoRecorderThread` pattern — rather than a moved-`QObject` `QThread`, because `PresetManager` is a *value member* of `pm::Bridge` and a `QThread` has no valid move. Requests coalesce latest-wins, so a burst of N rescans costs at most two directory walks, and a failed scan **retains the previous generation** instead of silently emptying a working library — the failure mode of a rescan is "my library is still there", never "my library vanished and I did not notice". The per-file `std::regex` was hoisted out of the scan loop, where it was compiling a grammar per preset — the dominant cost once the stat storm is paid — and replaced by a provably-equivalent `find('-') == npos` early-out. The synchronous `scan()` is **kept on purpose**: `pm::Bridge` reads `empty()` and `selectByIndex(0)` immediately after it and never sets a publish context, so it never starts a worker at all. A pinned-generation test fires 8 rescans and asserts the old pointers stay valid while a new generation appears at a different address, which is the invariant the copy-on-publish design exists to provide.
- **The startup preset list would have been permanently empty.** `PresetBridge::connectSignals()` was declared, defined, and called from nowhere, and because `qmlEngine_->load()` runs *inside* `init()`, QML's one-time `model:` binding evaluated before any async scan could publish — the list would have stayed empty for the life of the process while the scanner reported success. Wiring now happens in an idempotent `attachManager()` called from the constructor, so it is correct whether it is reached once or twice. This is the `AGENTS.md` §3 failure class — a declaration that reads as a working feature and is not — and it was surfaced *by* the fix above rather than independently: moving the scan to a worker alone would have shipped an empty library that no test could see, because the two defects are individually harmless and jointly fatal.
- **`Playlist` had no thread contract, and a mutex would have been the wrong fix.** It now carries a `const std::thread::id ownerThread_` with `assertOwnerThread()` on every public method — deliberately **not** a mutex, because a lock would *mask* an off-thread writer while `PlaylistBridge`'s row bookkeeping silently rotted underneath it, whereas the guard turns a heisenbug into a log line and an abort. The read API already returns values rather than borrowed views, so `PresetManager`'s shared-generation machinery has no reason to be replicated here; if a second thread ever does appear, the correct move is to marshal to the owner thread with `QMetaObject::invokeMethod(..., Qt::QueuedConnection)`, or to add exactly one coarse mutex **with every emit moved outside it**, since `currentChanged`'s live subscribers re-enter the playlist through the engine. **The backlog premise "UI and audio threads" was wrong twice:** the analyzer `JThread` was deleted when `spectrumUpdated` lost its last consumer, and `QMediaPlayer` is GUI-thread-driven — a `QObject` created in `init()` whose backend decodes on its own threads but delivers every signal to the object's thread. `DownloadQueue` has **no threads at all**: it is a plain `QObject` whose `setMaxConcurrent(3)` bounds in-flight HTTP replies multiplexed onto a single event loop, which nothing in its header says and which makes `addAndPlay` look dangerous to any reader who has not opened the implementation. **Two limitations recorded rather than papered over:** `assertOwnerThread` proves thread *affinity*, not re-entrancy safety — a slot re-entering the playlist from inside an emit is same-thread and passes, which is the current design working rather than a hole; and the `assert` compiles out under `NDEBUG` while the distributable build is Release, so a Release binary logs the violation and then walks into the race. That fail-loud-but-continue behaviour is accepted as the lesser evil against a false negative; a hard Release failure would need `std::terminate()`, not `assert`.
- **`LyricsSync` had two independent entry points into one read-modify-write.** The `QTimer::timeout` lambda and synchronous direct calls from `loadLyrics`, `seek` and `jumpToLine` all reached `updatePosition`, which is a read-modify-write over `smoothedTime_` (a `lerp`) plus a compare-then-write over `currentPos_` — so the two paths double-applied smoothing for a single audio instant and could drop or duplicate a `lineChanged` / `wordChanged` edge, in a class with no synchronization of any kind. `trackChanged` was additionally connected `Qt::DirectConnection` while its `stateChanged` sibling correctly used `QueuedConnection`, so a full state reset could run outside the event loop's ordering guarantees. The `QTimer` is now the **sole** writer, via a one-shot seed drained by a new public `syncNow()`; `seek` and `loadLyrics` seed rather than apply, and `trackChanged` is queued. A mutex was **deliberately not added** — two writers plus an unguarded `lyrics_.vector` would be strictly worse than the single writer now in place, and a lock would hide the second writer rather than remove it. Two subtleties are load-bearing: a seed must *snap*, which the drain achieves by pre-setting `smoothedTime_` so the lerp degenerates, or `seek` stops being exact and a mid-playback `loadLyrics` ramps from 0 instead of snapping; and `seek` with a null `AudioEngine` never drains on its own, which is what forced `syncNow()` to be public rather than a test-only backdoor. `AudioEngine::positionChanged` remains unconsumed and lyrics still poll — unchanged behaviour, and adding the second trigger would invite a second writer of exactly the state this change made single-owner.
- **Both `avcodec_alloc_context3()` results were unchecked.** A codec-allocation failure on the video path left a null `videoCodecCtx_` that setup code immediately wrote `width`, `height`, `time_base` and `framerate` through; the audio path had the identical shape with `sample_rate` and `bit_rate`. A resource exhaustion therefore became a null dereference mid-setup instead of an error the caller could report. Both allocations are now checked and return a named error alongside the existing stream-allocation checks.
- **`Playlist::loadM3U` followed relative entries out of the playlist directory.** A relative entry in an M3U is resolved against the playlist's own location, and nothing constrained the result — so a downloaded, synced or hand-edited playlist could name a file anywhere the process can read and have it silently appended to the queue, with nothing in the UI saying where the audio came from. Relative entries are now weakly canonicalized and rejected when they resolve outside the playlist directory.
- **The session selector re-derives the active session id from the access token's `sid` claim** rather than from `response.last_active_session_id`, which read as a deviation from the API master. - Dead audio plumbing removed: `pcmReceived` was emitted from the audio thread copying a `std::vector<f32>` per callback with zero receivers, and `currentSpectrum()` had no callers. `spectrumUpdated` likewise has none, so `currentSpectrum_` is now written once per analyzer tick for nothing.
- Fixed a latent build break: `rng_(std::random_device{})` does not compile under libc++ ("expects an lvalue for $1"). The checked-in static library had been built with a different toolchain and `ninja: no work to do` hid it, so any clean rebuild would have failed.

This release finalizes the `v1.1.0-BLEEDING_EDGE` line and is the first version whose source, executable, and release metadata are sourced from the same `version.txt` value.

### Added

- Suno-first desktop shell with Library, Create, Listen, Video, and standalone paged Settings surfaces.

- Credential/request epochs fence queued work, retries, auth waiters, and tracked replies across sign-out, replacement, and auth loss; direct uploads cancel on credential invalidation.
- Settings credential ownership is centralized in `SunoClient`; manual edits are debounced off the GUI thread and clearing keeps memory and durable storage coherent.
- Remote artwork, MP3 media, and direct upload URLs are restricted to exact capture-proven HTTPS origins with manual redirects.
- Clerk session selection requires an exact `last_active_session_id` match; undocumented Browser-Token synthesis and automatic `/tokens` fallback are disabled.
- Mutation POSTs are not automatically replayed after 401.

### Fixed

- QML root load failures now fail initialization instead of being logged as success.
- PFFFT scratch is aligned, per-call, immutable-setup backed, and protected from reset/analyze races; deterministic silence is returned on setup failure.
- Audio callback scratch is preallocated; oversized buffers are dropped without allocation.
- FBO, playlist, preset, database, theme, and config persistence failures now produce actionable logs.
- Cached QML bridge statics and application shutdown lifetimes are cleared in dependency order.
- Unit tests no longer write temporary playlists into the real user session file.

### Changed

- `version.txt` is the single source of truth for the CMake project, application version, and CPack version; invalid values fail configuration.
- Added the MIT `LICENSE` file referenced by the README/PKGBUILD and aligned the Arch package to `v1.1.0`.
- PFFFT is pinned to the tested revision; declaration-only Suno fetch declarations and stale legacy API surfaces are removed.
- Library search is explicitly local; the captured feed filter is not extended with unobserved `searchText` behavior.
- Unpromoted Range resume and redirect following remain disabled until capture-backed.

### Verification
